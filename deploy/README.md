# SIM Training: обновление и перенос

## Рабочая конфигурация с 23 ноября 2026

* Сайт: https://type-rating.survey-ebt.ru, VPS 129.101.92.158.
* SSH: deploy; код: /srv/sim-training/current; служба: sim-training.
* Фронт Nginx: /srv/sim-training/web; Django: 127.0.0.1:8010.
* Настройки: /etc/sim-training.env. После финального переноса DB_NAME=sim_training_live,
  MEDIA_ROOT=/srv/sim-training/shared/media-live. Скрипт не заменяет этот файл.
* На том же сервере работает LOSA. Скрипт не меняет его, Nginx, DNS или сертификаты.
* Старый SIM Training на 79.174.84.190 временно запущен для сравнения; переключение
  старого адреса на перенаправление пока не подтверждено. Старый сайт не обновляется этим скриптом.

## Обычное обновление

Запускать `./deploy.sh` **на Mac**, из проекта pilot_logbook, после коммита и push в main.
Для просмотра плана без подключения и изменений: `./deploy.sh --dry-run`.
Нужны Git, Node.js/Yarn, SSH/scp и SSH-доступ deploy к новому VPS. На VPS также
нужен доступ deploy к GitHub через уже настроенный ключ sim_training_github.
Скрипт может запросить пароль SSH и пароль sudo пользователя deploy; пароль БД
загружается из серверного EnvironmentFile и не выводится.

Последовательность: сборка React по yarn.lock на Mac → загрузка сборки в закрытую
временную папку → проверка точного совпадения Mac main и GitHub main → проверка
чистоты серверного checkout и отсутствия другого деплоя → остановка только
sim-training → резервная копия БД, настроек и предыдущего index.html → fast-forward
к проверенному коммиту → установка Python-зависимостей при изменении requirements
→ check, migrate, collectstatic → загрузка новых assets с сохранением старых
→ запуск Django и проверка ответа → атомарная замена index.html → проверка HTTPS.
Node.js на VPS не нужен. Загрузка справочников в media и содержимое БД не заменяются
локальными копиями. Для вкладки «Документация» обновляются и Django, и React.

Резервные копии: /srv/sim-training/shared/backups/deploy-… (закрытый каталог).
При ошибке скрипт останавливается. Если ошибка произошла после остановки Django,
служба может остаться остановленной; скрипт сообщает об этом. Причину смотреть:

```bash
sudo systemctl status sim-training --no-pager -l
sudo journalctl -u sim-training -n 60 --no-pager
```

Автоматического отката БД нет: после миграций старый код может быть несовместим
с новой схемой. Исправить причину и повторить деплой того же либо нового коммита;
после остановки службы при ошибке сначала проверить её вручную. Неприменённая
новая сборка не подменяет старый index.html. Копии и staging автоматически не
удаляются; очистку делать отдельно после успешной проверки.

## Первоначальный перенос (справочно)

Ниже сохранён первоначальный план переноса с прежним доменом survey-ebt.ru.
Для текущих обновлений использовать скрипт выше; первоначальные шаблоны Nginx
и окружения не копировать поверх действующих серверных настроек.

## Что переносить

* Полную PostgreSQL БД: пользователи, назначения, оценки, версии результатов,
  подтверждения ознакомления и история миграций. Выборочный экспорт здесь не нужен.
* Полный MEDIA_ROOT: загруженные документы, исходные таблицы и изображения.
* Код из Git, включая новый frontend и миграции 0005–0007.
* Секреты отдельно по защищённому соединению. Существующий production SECRET_KEY
  сохранить; пароль БД на новом сервере можно заменить. Секреты не добавлять в Git.
* Не копировать виртуальное окружение, node_modules или каталог PostgreSQL.

Резервная копия провайдера полезна дополнительно, но не заменяет свежий дамп.
Локальные черновики браузера не находятся в БД: до переключения завершить
и отправить незавершённые оценки.

## Сначала — пробное восстановление

1. Уточнить старый/новый IP, имя БД, пользователя, MEDIA_ROOT, путь приложения,
   способ запуска и версию PostgreSQL на старом сервере. Проверить A и AAAA домена.
   Новый PostgreSQL должен быть той же или более новой основной версии;
   pg_dump — не старше исходного сервера. Использовать совместимый pg_restore.
2. На старом VPS получить полный дамп и архив media. Скрипт ничего не удаляет:

   ```bash
   PGDATABASE=ИМЯ_СТАРОЙ_БД MEDIA_ROOT=/путь/к/media bash deploy/backup.sh /приватная/папка/резервных-копий
   ```

   Команду выполнять от пользователя с доступом к БД и media. При необходимости
   задавать PGUSER/PGHOST; пароль хранить в .pgpass с правами 600. На этапе
   окончательного переноса сначала остановить все записи в приложение и media.
3. Скачать созданную папку на Mac и передать на новый VPS через SSH (scp/rsync).
   Архив содержит реальные данные: хранить вне публичных каталогов, права 700/600.
   На новом сервере в папке архива выполнить `sha256sum -c SHA256SUMS`.
4. Создать отдельного владельца и ПУСТУЮ БД на новом PostgreSQL, затем:

   ```bash
   PGDATABASE=ИМЯ_НОВОЙ_БД bash deploy/restore_database.sh /приватный/путь/database.dump
   ```

   Скрипт откажется работать с непустой БД. Он не удаляет и не очищает существующие
   базы. Подключение должно вести именно на новый сервер. Восстановление идёт
   одной транзакцией без переноса старых владельцев и прав.
5. Распаковать media.tar.gz в пустой /srv/sim-training/shared/media, назначить
   владельцем пользователя приложения. Сравнить количество записей старой и
   восстановленной БД ДО новых миграций. `deploy/inventory.py` выводит только
   количества и номера миграций:

   ```bash
   python manage.py shell --verbosity 0 < deploy/inventory.py
   ```

   На старом сервере со старым кодом можно передать этот файл отдельно.
   Читаемость дампа и контрольные суммы сами по себе не доказывают успешное
   восстановление: обязательны фактическое восстановление и проверка данных.

## Новый сервер и новый фронт

* Отдельный системный пользователь simtraining; приложение
  /srv/sim-training/current; общие media и staticfiles — в /srv/sim-training/shared.
  Пользователь приложения должен иметь запись в media; Nginx — чтение dist и
  staticfiles и проход по родительским папкам. Не делать файлы доступными всем
  на запись. MEDIA_ROOT не публиковать через открытый Nginx alias.
* Установить Python 3.12 (Ubuntu 24.04), venv, PostgreSQL, Nginx и Node.js 22.12+
  с Yarn 1.22. Собрать зависимости на новом сервере, проверить их совместимость:

  ```bash
  python3 -m venv .venv
  .venv/bin/pip install -r deploy/requirements-production.txt
  ```

* Скопировать production.env.example в /etc/sim-training.env, заменить все
  заглушки, владелец root, права 600. Сохранить старый production SECRET_KEY.
  Для команд управления безопасно загрузить переменные в окружение, либо
  выполнить их через служебный запуск с EnvironmentFile. Файл подходит для
  systemd; не выполнять его через shell без проверки синтаксиса значений.
* ПОСЛЕ восстановления старой БД выполнить с production окружением:

  ```bash
  .venv/bin/python manage.py check --deploy
  .venv/bin/python manage.py showmigrations
  .venv/bin/python manage.py migrate --plan
  .venv/bin/python manage.py migrate
  .venv/bin/python manage.py collectstatic --noinput
  yarn --cwd frontend install --frozen-lockfile
  yarn --cwd frontend build
  ```

  Новые таблицы версий результатов будут заполнены миграцией: их рост ожидаем.
  Сравнить количество пользователей, сессий, упражнений и оценок после миграций.
  Не запускать migrate на пустой базе перед полным восстановлением старой схемы.
* Установить sim-training.service в systemd; nginx.conf адаптировать к реальным
  путям и сертификатам. Gunicorn доступен только на 127.0.0.1:8010. React отдаётся
  Nginx, /api/, /admin/, печать и защищённые /media/ — Django. Vite dev server
  на VPS не запускать. Загрузка файлов вне docs/*.pdf доступна только персоналу;
  PDF в docs — авторизованным пользователям, как существующий список документов.
* До переключения DNS подготовить сертификат survey-ebt.ru: DNS-проверка для
  выпуска сертификата либо защищённый перенос действующего сертификата и ключа.
  Обычная HTTP-проверка нового сервера не сработает, пока домен ведёт на старый.
  Настроить продление сертификата. Проверить `nginx -t` перед применением.
* Проверить новый VPS с прежним именем через локальное сопоставление домена/IP,
  не меняя публичный DNS: вход инструктором/слушателем, календарь, оба пилота,
  прошлые замечания, сохранение оценок, ознакомление, история, исправления, печать,
  Django admin, загрузка файлов и отказ доступа без входа. Пробные изменения
  останутся в пробной БД и не должны переноситься обратно в рабочую.

## Окончательное переключение

1. Согласовать короткий перерыв. На старом сервере включить обслуживание и
   остановить все источники записи, включая фоновые задачи. Не только веб-процесс.
2. Сделать СВЕЖИЙ полный дамп и архив media, перенести и проверить контрольные суммы.
3. На новом сервере использовать новую ПУСТУЮ окончательную БД (не пробную),
   восстановить дамп и media, выполнить миграции и сверку, затем проверить вход.
4. Переключить DNS A на новый IPv4; проверить AAAA и убрать старое направление,
   если IPv6 на новом сервере отсутствует. Домен и адреса API останутся прежними.
5. Старый сервер оставить в обслуживании: во время обновления DNS два сервера
   не должны одновременно принимать изменения в разные базы. Проверить HTTPS,
   загрузку фронта, API, печать и запись на новом сервере, следить за ошибками.
6. После настройки нового Git-репозитория отдельно изменить production remote.
   Переключение DNS не меняет адрес Git, если remote содержит старый IP.
7. Сохранить старый сервер и резервные копии до подтверждения результатов.
   После появления новых записей простой возврат DNS к старой БД потеряет их:
   для такого отката сначала требуется перенос или согласование новых данных.

Автоматические резервные копии, проверку восстановления и обновление
зависимостей безопасности настроить до начала регулярной работы на новом VPS.
